# Markdown 文档写作规范

本规范用于统一 Markdown 文档的写法，可直接复制到任意项目中作为写作与审校依据，也适合作为 AI 编写文档时的指令。

全文与具体项目无关。示例均为通用示例，套用时替换为项目自身的命令与名词即可。

## 1 总则

### 1.1 以读者要完成的事为准

动笔前先明确读者是谁、他要做什么，全文只服务这个目的。

一句可操作的判断法：**删掉这句话，读者还能不能做对？会不会因此踩坑？**

- 能 → 删。
- 不能 → 留，并压到最短。

按这条筛，被删掉的多是「讲机制」的句子——读起来专业，但不改变任何操作。

| 可以删的句子 | 为什么 |
|---|---|
| 「该命令内部先读取配置，再合并环境变量」 | 读者只需知道何时运行它，不需要知道内部顺序 |
| 「该文件在构建阶段被解析」 | 读者只需知道"执行下一步之前它必须存在" |
| 「该现象由虚拟化组件的端口保留造成」 | 知道成因也改变不了修复命令 |

**唯一例外是排查章节。** 那里机制就是诊断手段——读者正是靠「配置合并只读取引用行上方定义的变量」去定位问题。这类必须保留。

### 1.2 同一条警告只说一次

在**动手的那一步**完整写一次，排查章节用一句指回去：

> 详见 3.3 节

不要把同一段理由在多个章节重述。同一条警告出现在三处，是文档显得啰嗦的主因。

### 1.3 操作与参考分开

把「按顺序执行的步骤」和「按需查阅的资料」分到不同章节，步骤章节内部不插入参考资料，读者才不必读无关内容。

可用的骨架：

| 章 | 性质 |
|---|---|
| 安装 / 搭建 | 按顺序执行，步骤之间有依赖 |
| 日常使用 | 常用流程 |
| 故障排查 | 按现象查 |
| 配置 / 参数参考 | 查阅，非步骤 |

### 1.4 删掉的内容要有去处

按 1.1 删去的内容若属设计取舍、实现机理，不要直接丢弃，应落到代码注释或专门的设计文档中——文档读者不需要它，维护者需要。

删除后应在提交说明或评审意见中指明去向，避免他人误以为信息丢失。

## 2 语体

### 2.1 书面语、第三人称、完整句

- 不用口语词：~~跑起来~~ → 运行；~~卡住了~~ → 失败；~~搞定~~ → 完成。
- 不用表情符号，提示改为 `> **注意**：`。
- 不用感叹语气，不用「我们」。
- 一句讲一件事，不要将几个意思挤进一个长句。

| 不要 | 改为 |
|---|---|
| 把服务跑起来 | 启动服务 |
| 卡住了看下面 | 失败时参见 3.1 节 |
| 三条原因长得都像「密码错」 | 以下三种原因的现象均表现为「密码错误」 |
| 或者临时绕过 | 亦可临时绕过 |

### 2.2 加粗与强调要节制

加粗只用于三处：句首的行内标题、术语首次定义、会导致错误或数据丢失的后果。

不要整句加粗，不要连续多行加粗。需要小标题的地方就用小标题，不要用加粗顶替。

### 2.3 列表与段落的分工

并列且互不依赖的短项用列表；有因果、条件、递进关系的用段落。

常见的错误是把一段本有逻辑关系的说明拆成三四个短句列表，读起来像提纲而不是说明。

## 3 代码块

### 3.1 块的类型

代码块分四类，规则不同。

| 类型 | 特征 | 规则 |
|---|---|---|
| 命令块 | 读者会复制去执行 | 一块一条命令，见 3.2 节；标注语言（`bash`、`powershell` 等） |
| 输出块 | 程序打印的结果 | 可多行，不标语言 |
| 记法块 | 接口签名、公式、伪码等非命令 | 可多行；不标语言，或标对应语言 |
| 示例数据 | 请求体、响应体等 | 可多行；标 `json` 等 |

判断依据是**读者是否会点复制按钮**：会复制的按命令块写，不会的归入其余三类。给非命令块标上 `bash` 会误导读者去复制。

### 3.2 一个命令块只放一条命令

- 不把多条命令堆在一个块里。
- 不在行尾写 `#` 注释——复制出来还得手动删。

说明写在代码块**外面的引语**里。

反例：

```bash
npm run build    # 构建
npm test         # 测试
```

改为：

构建：

```bash
npm run build
```

测试：

```bash
npm test
```

由续行符（`\`）连接的多行**仍算一条命令**，应放在同一个块里。

### 3.3 行内代码与代码块的分工

出现在句子中间的标识符、路径、变量名、字段名用行内代码。整条可执行的命令一律用代码块。

### 3.4 表格中的命令

以扫读为目的的速查表，可以在单元格里用行内代码列命令，不强制可复制。

但主流程中要求读者执行的命令必须放进代码块，不能只写在表格单元格里。

## 4 表格

### 4.1 表格必须有引语

表格不能直接跟在段落或标题后面悬着，前面要有引出它的句子。

反例——表格悬空：

```markdown
### 1.1 依赖

| 软件 | 版本 |
```

改为：

搭建前应确认以下软件的版本：

| 软件 | 版本 |
|---|---|
| Node.js | ≥ 20 |

### 4.2 不用「表 1」「表 2」

不给表格加编号题注。正文引用改用「如下」「见下文」，或直接复述，不要写「见表 2」。

### 4.3 行数多时按主题分组

一张大表按读者会问的问题拆开，各组加小标题。参数参考表可按「必填 / 存储 / 服务 / 限额」等维度分组。

### 4.4 单元格保持简短

单元格里放一句话。超过一句话、需要举例或附代码的内容，改写成独立小节。

## 5 章节与引用

### 5.1 编号

- 正文各章用 `1` / `1.1` / `1.2.1`，不用「一、二、三」。
- 引言、概览、附录一类的前后置内容不编号，以免与正文序号混淆。

### 5.2 交叉引用

- 同文档：`详见 3.3 节`。
- 跨文档：`见 DOCKER.md 第 2 章`，带上文件名以便跳转。

引用要指到最小可定位单元（某一节或某一步），不要只写「见上文」。

### 5.3 改动编号后必须同步引用

**改动章节编号后，必须同步修改其他文档中指向它的引用。** 多篇文档互相引用小节号是常态，编号重排会让引用一并失效。

## 6 文件格式

- 行尾统一用 LF。Windows 上的编辑器与工具常默认写成 CRLF，提交前需确认。
- 不用 BOM。
- 文档之间的链接用相对路径。
- 若仓库有 `.gitattributes`，按其规定设置 Markdown 的行尾。

## 7 事实一致性

文档中出现的文件路径、配置项默认值、域名、端口、命令输出，都必须与仓库实际状态一致。

这类内容最容易在重构后失效，而且失效时不会报错，只是把读者引向错误的地方。改动以下任一内容后，应全仓库检索并更新引用：

- 标题与编号
- 文件路径与文件名
- 配置项的默认值
- 示例中的域名、端口、镜像标签

## 8 提交前自查

- [ ] 每句话都通过了「删掉它读者还能做对吗」
- [ ] 同一条警告全文只完整出现过一次
- [ ] 删去的设计取舍已落到代码注释或设计文档
- [ ] 命令块每块恰好一条命令、无行尾注释
- [ ] 非命令块没有被标成 `bash`
- [ ] 每张表格都有引语
- [ ] 无「表 N」编号，无表情符号
- [ ] 章节编号改动后，其他文档中的引用已同步
- [ ] 文件路径、默认值、域名、端口已与仓库核对
- [ ] 行尾为 LF
